# Representation beats algorithm — a case study on a rule-generated PCOS dataset

> **Read this first.** The labels in this dataset are produced by a deterministic four-condition
> rule. That makes 100 % accuracy attainable and, on its own, uninformative. This project finds
> the rule, proves the pipeline is leakage-free, and then uses the dataset for the thing it *is*
> good for: showing that **how you represent the data matters more than which algorithm you pick**.
>
> **None of the numbers here are clinical performance.** See [Honest limitations](#honest-limitations).

---

## The result in one table

Seven algorithms, five feature representations, 5-fold stratified cross-validation. Same data,
same folds — only the representation changes.

| Algorithm | raw (5 cols) | scaled (5) | **engineered (9)** | lean (4) | count (1) |
|---|---:|---:|---:|---:|---:|
| Gaussian Naive Bayes | 72.12 % | 67.38 % | **100 %** | 100 % | 100 % |
| SVM (RBF) | 80.12 % | 96.50 % | **100 %** | 100 % | 100 % |
| K-Nearest Neighbours | 80.62 % | 96.37 % | **100 %** | 100 % | 100 % |
| Logistic Regression | 91.00 % | 91.00 % | **100 %** | 100 % | 100 % |
| Decision Tree | 99.88 % | 99.88 % | **100 %** | 100 % | 100 % |
| Random Forest | 99.88 % | 99.88 % | **100 %** | 100 % | 100 % |
| HistGradientBoosting | 99.88 % | 99.88 % | **100 %** | 100 % | 100 % |

Three things worth pausing on:

1. **On raw inputs the algorithms span 67 % → 99.9 %** — a 33-point spread driven entirely by
   model choice.
2. **After encoding four threshold indicators, that spread collapses to zero.** Every algorithm
   reaches ceiling, including the Naive Bayes that was 33 points behind. The bottleneck was never
   the classifier.
3. **Scaling helps exactly the models theory says it should.** SVM 80 % → 96 %, KNN 81 % → 96 %,
   and the trees do not move at all — they are invariant to monotone rescaling.

A single integer column (`count`) also reaches 100 %, which is the sharpest statement of how much
work the representation was doing.

---

## Why the ceiling exists

Systematic EDA showed the target is not stochastic. It is generated by a conjunction:

```python
PCOS = (Menstrual_Irregularity == 1) and (BMI > 25) and (Testosterone > 40) and (Antral_Follicle_Count > 10)
```

This reproduces **1,000 / 1,000 labels with zero errors**. The Bayes error is zero, so perfect
accuracy is attainable in principle and any shortfall is a limitation of the model class rather
than irreducible noise.

The fingerprints of synthetic generation are all present: every feature uniformly distributed and
mutually independent (max |r| = 0.05), zero missing values, zero duplicates, zero outliers under
IQR / z-score / Mahalanobis, round clinical cut-points, and no label noise whatsoever. Real
clinical cohorts do not look like this.

---

## Is the 100 % real, or is something leaking?

Worth being suspicious of. Four checks, all in the notebooks:

| Check | Result |
|---|---|
| Test rows sharing a feature vector with train | **0 of 200** |
| Scaler parameters equal train statistics, not full-data statistics | ✅ (test set does **not** centre on zero — the residual offset is the proof) |
| Cut-points re-derived independently in all 5 CV folds | identical every time, **zero variance** |
| **Falsification: randomly flip 5 / 10 / 20 / 40 % of labels** | accuracy → **95.0 / 90.0 / 80.0 / 60.0 %** |

That last row is the decisive one. A leaking pipeline would have stayed near 100 % regardless of
how corrupted the labels were. Instead accuracy tracks the noise ceiling almost exactly, which is
what an honest pipeline must do.

## What the preprocessing actually does

A data-quality audit of 13 checks passed **13/13** on the raw file — no missing values, no
duplicates, no contradictory labels, no out-of-range values, no outliers, no multicollinearity, no
skew. So the notebook is as much a record of what *not* to do as what to do: imputation,
winsorising, log / Box-Cox transforms, PCA and resampling were each considered and each **ruled
out with evidence**, because applying them would cost signal and buy nothing.

Four things were genuinely needed:

1. **Rename** `Testosterone_Level(ng/dL)` → `Testosterone`. XGBoost and LightGBM reject `(`, `)`
   and `/` in feature names.
2. **Standardise** the continuous columns — for the distance- and gradient-based models only.
   Worth 16 points to SVM-RBF and, correctly, nothing at all to the trees.
3. **Split early and stratified**, so every fitted transform sees training rows only.
4. **Encode the discovered thresholds as features.** This is where nearly all the value is.

### The methodological point

The EDA discovered the cut-points by fitting a tree to **all 1,000 rows — test set included** —
and hard-coding them. That is fine for *understanding* the data and wrong for *reporting a score*.

The preprocessing replaces it with `ClinicalThresholdEncoder`, a supervised transformer that
re-derives cut-points inside `fit()` from whatever rows it is handed, then snaps them onto
published clinical values (WHO BMI classes, female testosterone reference, Rotterdam AFC) only
when a training-set guard confirms the snap is not a downgrade. Dropped into a `Pipeline`, it is
re-fitted per fold, so a validation fold never contributes to the thresholds used to score it.

All five folds independently recover `BMI > 25`, `Testosterone > 40`, `AFC > 10` — zero variance.

### A redundancy defect caught by self-audit

Section 2.6 held the *input* data to a multicollinearity standard (VIF ≈ 1.00). Applying the same
standard to the *engineered* output caught a real problem: `criteria_met` is not merely correlated
with the four indicators, it is **exactly their sum** — an exact linear dependency that pushed the
design matrix VIF to 1e12 while changing no model's accuracy. It was removed from `engineered`
(max VIF falls to **4.12**) and shipped as its own one-column `count` space.

Two further checks came back negative and are recorded rather than hidden: removing `Age` does not
help, and the two candidate ratio features are weaker than the columns they are built from.

## The models

Three models, all executed on an NVIDIA RTX 4050 (CUDA 12.6). Two from the same family and one
deliberately different, so the result is not an artefact of picking models whose shape flatters
the data.

| Notebook | Model | Why it was chosen |
|---|---|---|
| `model/01_xgboost_gpu.ipynb` | XGBoost, `device="cuda"` | Boosted trees represent axis-parallel rules exactly — the same shape as the target |
| `model/02_catboost_gpu.ipynb` | CatBoost, `task_type="GPU"` | Symmetric (oblivious) trees: a depth-4 tree *is* a 4-condition conjunction. Ordered boosting removes target leakage from the gradient |
| `model/03_pytorch_mlp_gpu.ipynb` | PyTorch MLP (64→32) | A different family entirely — a smooth surface with no built-in notion of a threshold |

### Held-out test set — 200 patients, untouched until evaluation

| Model | Accuracy | Recall | F1 | MCC | Brier | Mean margin | 5-fold CV |
|---|---:|---:|---:|---:|---:|---:|---:|
| XGBoost (GPU) | 1.000 | 1.000 | 1.000 | 1.000 | 4.7e-06 | 0.9957 | 1.000 ± 0.000 |
| CatBoost (GPU) | 1.000 | 1.000 | 1.000 | 1.000 | 9.4e-10 | 0.99995 | 1.000 ± 0.000 |
| PyTorch MLP (GPU) | 1.000 | 1.000 | 1.000 | 1.000 | 2.9e-10 | 0.99997 | 1.000 ± 0.000 |

Zero false negatives, zero false positives, all three.

Because accuracy saturates, each notebook adds a **decision-margin** section — how far from the
boundary each prediction sits — since that is the only metric that still discriminates between the
three models.

Each notebook contains nine evaluation views: performance matrix (13 metrics), confusion matrix,
ROC, precision-recall, probability distribution, calibration curve, threshold sweep, decision
margin, feature importance, training curve, cross-validation and error analysis.

### A bug worth documenting

XGBoost initially stopped at **iteration 0** — a single tree, margin 0.05, Brier 0.226. Cause:
XGBoost early-stops on the **last** metric in `eval_metric`, and `error` hits 0.0 at round 0 on
separable data, so it can never improve. Reordering to `["error", "logloss"]` gave 206 trees and a
Brier of 4.7e-06. The notebook keeps a sanity check for this.

### On the GPU, honestly

All three genuinely ran on CUDA — the device is read back from the trained booster's own config,
not from what was requested. But the GPU was **slower every time**:

| Model | GPU | CPU | Speed-up |
|---|---:|---:|---:|
| XGBoost | 2.8 s | 0.5 s | 0.19× |
| CatBoost | 48.3 s | 1.3 s | 0.03× |
| PyTorch MLP | 44.2 s | 28.3 s | 0.64× |

That is expected, not a fault. 800 rows × 9 features is ~45 KB; kernel-launch and PCIe overhead
dwarf the arithmetic, and the crossover is around 10⁵–10⁶ rows. Each notebook measures this rather
than asserting it, and confirms GPU and CPU produce **identical predictions**.

```
│   ├── 01_xgboost_gpu.ipynb            # GPU gradient boosting
│   ├── 02_catboost_gpu.ipynb           # GPU ordered boosting, symmetric trees
│   ├── 03_pytorch_mlp_gpu.ipynb        # GPU neural network
│   └── results/                        # trained models + metrics JSON
├── data/processed/                     # 5 feature spaces × train/test
└── artifacts/
    └── preprocessing_metadata.json     # cut-points, scaler params, cleaning log, recipe
```

Run them in order: `eda.ipynb` → `preprocess.ipynb` → any notebook in `model/`.
All notebooks are committed **with outputs**, so GitHub renders the charts without running anything.

### No `.py` files, and no pickled pipelines

Everything is notebook-only. That has a consequence worth knowing: `joblib` records a custom class
by import path, so a transformer defined in a notebook serialises as
`__main__.ClinicalThresholdEncoder` and **cannot be reloaded from any other process**. A `.joblib`
that only opens in the session that wrote it is worse than none, because it looks like a working
artefact.

So instead of pickling, `preprocess.ipynb` saves a **JSON recipe** — learned cut-points,
imputation fills, scaler mean/scale — and asserts that re-applying it in plain pandas reproduces
the pipeline output exactly for all five feature spaces. Scoring a new patient is ~15 lines with no
imports.

The three model notebooks require an NVIDIA GPU with CUDA. To run them on CPU instead, change

card and fail with `CUDA out of memory`.

## Honest limitations

1. **This is not clinical performance, and must not be presented as such.** The labels come from a
   deterministic rule, so a model that recovers the rule is perfect by construction. Real
   Rotterdam-criteria diagnosis is probabilistic, involves ultrasound morphology and the exclusion
   of other disorders, and no real cohort separates at 100 %.
2. **The dataset is synthetic.** Uniform independent features and noise-free labels are generator
   fingerprints, not properties of PCOS.
3. **`lean` and `count` are lookup tables.** With 4 binary columns only 2⁴ = 16 distinct vectors
   exist, so every test patient reuses a vector seen in training. That is not leakage — the
   cut-points were still learned from training rows only — but their 100 % should be read as "the
   rule is exact and no cell is empty", not as generalisation to novel inputs. `raw` and
   `engineered` make the stronger claim: there, all 200 test vectors are unseen.
4. **`Menstrual_Irregularity` is constant within the positive class**, so the class covariance
   matrix is singular in *every* feature space including `raw`. Estimators that invert a per-class
   covariance (`QuadraticDiscriminantAnalysis`, some LDA solvers) need `reg_param > 0`.
5. **No hyper-parameter search was run.** Parameters were chosen from the structure of the target
   (`max_depth=4` for a four-condition rule) rather than tuned, since the ceiling is reached
   immediately and tuning would measure nothing.

## What would make this stronger

Point the same pipeline at a real PCOS cohort — the Kerala dataset (~540 patients, 40+ features)
is a common public choice. The methodology transfers directly: contract, audit, stateless clean,
early stratified split, fitted transforms, falsification test. On real data the imputer and class
weights would stop being no-ops, accuracy would land somewhere realistic, and the model comparison
would actually have a winner.
